# Reference cards

Reference cards are how CDX Studio keeps a character, place or object consistent across shots. Four
kinds: **character**, **location**, **prop**, **movement**.

Each image-based card owns a grid of named slots with one lifecycle:

```
empty → generating → review → accepted
```

Two rules matter more than the rest:

- **Regenerate keeps the accepted image** until a new candidate is accepted, so a slot is never left
  bare mid-flight.
- **Accepting is a human act.** A finished generation lands in `review`, never straight into
  `accepted`. Do not auto-accept on someone's behalf.

## Character — the anchor cascade

Characters gate hardest, because identity drift is the most visible failure:

1. `close_up_face` — accept this first. It unlocks:
2. `full_body` — accepting this unlocks:
3. body fields (height, weight, body type) **and** the auto set: `side_view`, `seated`, and six
   emotions (happy, sad, angry, surprised, fearful, disgusted).

Until **both anchors are accepted**, the character is `partial` in the context stack and generation
will produce off-model shots. This is the most common reason a shot comes back wrong.

The accepted anchors become the reference images for generation: close-up as `referenceImage1`, full
body as `referenceImage2`.

### Wardrobe

A character can carry wardrobe variants. When one is active, its filled slots win per-slot over the
base anchors, and unfilled ones fall back. Wardrobe deliberately does **not** move the blocking
identity lock — the identity stays pinned to the base anchors while the clothes change.

## Location

Slots: `wide`, `medium`, `detail`, `birds_eye`. The accepted `wide` plate is the reference image the
context stack contributes.

Locations also carry **landmarks** — labelled positions in meters (`{ name, x_m, y_m }`) that feed
the blocking environment footprint directly. If a scene needs characters positioned relative to real
features, put the landmarks on the location card.

## Prop

Slots: `hero`, `alt_1`, `alt_2`. The accepted `hero` shot is what generation references. Simple, no
cascade.

## Movement (kimodo)

The fourth kind, and the odd one out: a movement's product is **motion data**, not an image, so it
has no slot grid — just the one lifecycle.

A movement binds **one named action to one character**:

- `prompt` — the action in plain language, e.g. "throws a right hook then backpedals".
- `characterId` — which character performs it.
- `params` — `frames` (default 90), `steps` (30), `seed` (42).

Generated by a local kimodo.cpp service as SMPL-X22 (22 joints). Only metadata is stored in the
project; the per-frame rotation and root-translation arrays stay on disk behind `out_dir`.

A movement contributes its action line to the prompt **whether or not** the motion clip has been
accepted — the words describe the beat, the clip drives the rig.

### Multi-character beats

For a fight or a chase, generate one **scene** rather than unrelated single clips, so every track
shares one arena coordinate space with per-character `root_offset` and `facing_deg`.

## Diagnosing "why is this blocked?"

Resolve the context stack and read the gaps. In practice it is almost always one of:

- a character with unaccepted anchors (`partial`);
- a shot naming a character, location or prop that has no card at all (`missing`);
- a movement assigned to a character id that no longer exists;
- a location with landmarks but no accepted wide plate.
